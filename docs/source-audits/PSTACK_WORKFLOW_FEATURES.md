# Pstack ordinary workflows and engineering principles: adoption audit

Source pinned at `23e4138daa01c42d4969f7a5465f82704e64f798` in `cursor-plugins/pstack`. This report covers `how`, `why`, `recall`, `architect`, `teach`, `blast-radius`, `tdd`, `typescript-best-practices`, `figure-it-out`, `show-me-your-work`, all 24 principle skills, and the ordinary Investigation, Bug fix, Feature, Refactoring, Prototype, Perf issue, Runtime forensics, and Trace forensics playbooks. The `poteto-mode` wrapper and Opening a PR were read to establish inherited behavior. This was a source audit: no private transcripts or shared-account histories were read, no external application was mutated, and no original skill or adoption kit was edited. The checkout's HEAD was checked against the pin; all 24 principle directories were counted.

## Adoption judgment

Adopt the evidence contracts and task distinctions. Adapt the orchestration. The strongest changes to everyday work are: prove the load-bearing claim by executing the real path; distinguish understanding, changing, and measuring; pin behavior before refactoring; scope historical evidence and label inference; isolate concurrent writers; and let workers own independently answerable questions and their evidence. These work across projects without the author's full tooling stack.

Installing Poteto Mode unchanged has a worse tradeoff for this user. Its strongest ideas arrive with compulsory routing, model defaults, fixed fan-out, todo copying, prose rules, commit policy, and PR creation. That raises the cost of small tasks and makes the agent's responsibilities more prescriptive than necessary. `automate-me` can turn selected practices into local adoption artifacts; it does not establish the value of the rest of the stack and is not a reason to exclude the ordinary workflows from evaluation.

Scores below are **adoption value for this user's future Cursor work**, including selective adaptation: **5** = adopt early, **4** = strong with clear scope or edits, **3** = situational, **2** = mostly avoid as a default, **1** = poor fit. A high score is not an endorsement of every source clause. The adjacent recommendation makes that distinction concrete. Source notation such as `how:24` means the numbered line in that skill's `SKILL.md`; a playbook name means `skills/poteto-mode/playbooks/<name>.md`.

## Consequential gaps and contradictions

1. **Adaptive workers versus fixed or compulsory staffing.** `how:24` requires 2–4 explorers, `how:34` still spawns for a simple question, `why:94–100` assigns one investigator per available category, `architect:35` requires at least two candidates, and `feature:12` mandates delegates and sometimes arena. There are sensible responsibility contracts underneath: explorer traces one angle, historian gathers one source, synthesizer reconciles/spot-checks, implementation owner holds one coherent diff, reviewer inspects evidence. Adopt those responsibilities and select staffing from uncertainty, independence, expected evidence gain, and budget. Zero workers is sometimes correct. One or more can be correct when each owns a distinct question; there is no project-independent target count.

2. **Provider policy is not the mechanism.** `how:11,27,37,47`, `why:13,84,128`, `architect:33`, and `poteto-mode:95` depend on `pstack-models.mdc`, Cursor Task fields, and concrete provider model slugs. The source documents rejected-slug fallbacks, but this audit did not verify availability in an installed Cursor session. Inherit the current model unless the user deliberately configures alternatives. Independent responsibility, blind alternative generation, and a separate verification role have value without assuming a particular model family. Agent agreement is not evidence of runtime correctness, despite `poteto-mode:97` calling it high-signal.

3. **Broad wrapper rules override more adaptive leaf skills.** The TDD skill says do not force a costly regression harness (`tdd:11–26`), but the wrapper requires architecture on every function boundary and the feature playbook makes delegation compulsory (`poteto-mode:22`; `feature:12`). The standalone API migration principle excludes external users (`principle-migrate-callers-then-delete-legacy-apis:17–20`), while Refactoring tersely bans compatibility shims (`refactoring:11`). Teach requests narrow `why` searches (`teach:14`), but Why only allows unavailable/provably-irrelevant skips and makes inline answers rare (`why:116–121`). Use the narrowly scoped contract and explicit project constraints instead of resolving these tensions by maximum ceremony.

4. **“Read-only” does not fit every permitted action.** Runtime forensics offers CDP injection or a live hotfix (`runtime-forensics:7`) and then labels itself read-only (`:9`). Scope local observation separately from live mutation. A source audit, like this one, does not grant instrumentation of a user's production process. Similarly, the wrapper's blanket “Use any MCP tool” and team-chat/ticket/eval autonomy (`poteto-mode:83`) is broader than the standalone reversible-code principle and this user's permission boundary.

5. **Verification heuristics contain incorrect examples.** `principle-test-behavior-not-implementation:15–18` says output assertions including `toBeDefined`, `toBeTruthy`, `toBeInstanceOf`, and `toBeGreaterThan(0)` still pass if imports return `undefined`. On subject output, those assertions ordinarily fail for `undefined`; weak discrimination among wrong non-undefined values is the actual problem. Absence or call assertions can also prove valid behavior when paired with an appropriate mechanism test. Separately, `typescript-best-practices/references/patterns.md:80–84` says a negative range cannot be written with `{ start: Date; durationMs: number }`, but `durationMs: -1` is a valid value of that supplied type. The model changes the representation; it does not prove nonnegative duration. Correct these before reusing the examples as teaching or deletion rules.

6. **Delivery defaults exceed an ordinary local task.** The code playbooks all route to Opening a PR (`bug-fix:13`; `feature:17`; `refactoring:14`; `perf-issue:20`). That playbook proposes worktrees, rewriting commits, a CLI/tool forge policy, and ready PRs rather than drafts (`opening-a-pr:5–9,26–32`). Those are useful when authorized delivery requires them, not prerequisites for a local demonstration. Its suggested `git reset --hard` between same-branch delegates (`:5`) needs actual ownership and preservation of unrelated changes. Prefer separate writable ownership and concrete review artifacts. Do not silently change another project's review/readiness conventions.

7. **Audit artifacts are not concurrency control.** The log helper appends a TSV, creates its header if empty, and escapes spreadsheet formula-leading cells (`show-me-your-work/scripts/log.sh:19–42`). This is a useful small implementation. It does not lock a shared file or verify that evidence pointers resolve. Use a single log owner or per-worker logs merged by the owner; independent writes to one canonical log conflict with separate-before-shared-state. A well-formatted log is still a claim until its evidence is checked.
