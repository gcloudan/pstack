# Pstack verification, review, experiments, and writing adoption audit

Audited source: `cursor-plugins/pstack` at `23e4138daa01c42d4969f7a5465f82704e64f798`, plugin version `0.15.6`. The checkout SHA was read directly. This is a source audit, not a report that these workflows were run successfully. No source or personal kit was changed. No private transcript or external tracker was read or changed. Ratings and proposed adaptations are engineering judgments about useful carry-over, not claims about the author's private intent.

This slice covers verification generation and maintenance, parallel coverage and alternative generation, adversarial review, experiments, comment review, and prose. It complements the broader pstack feature inventory. Personal preference extraction through `automate-me` is not the scope of this file.

Scores mean 5 = strong default mechanism to carry over; 4 = strong situational workflow; 3 = useful after substantial adaptation; 2 = retain only selected ideas; 1 = do not carry over the current prescription. The score is adoption value for the mechanism, not a measured effectiveness score. Source pointers below are relative to `cursor-plugins/pstack`; ranges identify the evidence, not executable guarantees.

## The review and lane counts are different mechanisms

`interrogate` does not specify ten lanes. It defaults to three reviewers, one per configured model entry, receiving the same intent and rubric. The rubric's actual top-level lenses are Correctness; Root Causes vs. Symptoms; Structural Integrity; Verification; Complexity Budget; and Security. The additional code-quality file has eight numbered dimensions, numbered 0 through 7. These are review lenses, not separate worker seats. `skills/interrogate/SKILL.md:34-57`; `references/rubric.md:5-77`; `references/code-quality-review.md:17-35`.

The plan author must invent nine scenarios for the particular PR. The same playbook separately demands gates, perf, and two or more diff/receipt audits, which brings its minimum verifier count to 14, in addition to PR owners and the coordinator (`:65-71`). `autopilot-full.md:8` uses required categories and two or more audit lanes but does not itself fix ten live lanes.

The carry-over should be a coverage matrix with a reason for every scenario. Unit, real app behavior, comparison to current behavior, performance, concurrency, persistence, and accessibility apply when the change touches those concerns. A harmless documentation PR needs no contrived app screenshot or perf metric. A concurrency migration may deserve more than ten scenarios. Scenario count and concurrent worker count must be separate.

## Adaptive workers should be the default

The source already allows useful adaptation. `swarm` sets N from the user or the shape, and explicitly distinguishes total workers from concurrency limits (`skills/swarm/SKILL.md:22-26`). `arena` can use more candidates for distinct design directions and the same model repeatedly for generation-bound work (`skills/arena/SKILL.md:27-29`). The guide says to use more candidates when a decision matters and fewer when it does not (`docs/guide/04-design.md:43-46`). The fixed ten-lane plan contradicts that otherwise sensible economy.

For carry-over, start with required evidence and independence boundaries, then choose workers. Use one owner for a shared live app session; parallelize source reading. Give writing workers isolated output paths or worktrees. Batch small related features in one source reader. Use two or three competing implementations when reversing the wrong design would be costly. Add reviewers when a distinct model or domain check can change a decision. Do not multiply seats merely to repeat the same prompt against the same missing context.

Bound concurrency by runtime slots, app isolation, data ownership, machine contention, and token/time budget. Measurement lanes can contend with each other and corrupt a comparison even when code work is independent. Stop adding workers when they add only repeated prose or consume the coordinator's review budget. Record dropped workers and uncovered slices. These adaptations are recommendations, not features implemented by pstack's runtime.

## Agreement and observation support different claims

Pstack gives agreement considerable weight: `interrogate` treats findings raised by two or more models as highest signal (`skills/interrogate/SKILL.md:63-67`), `arena` calls convergence a strong agreement signal (`skills/arena/SKILL.md:61`), and `reflect` gives convergent findings higher confidence (`skills/reflect/references/synthesizer.md:18`). This is a useful prioritization hint, not independent factual confirmation.

Reviewers share the same task, source, rubric, and often similar training. Different model families can still share blind spots. Agreement can repeat the same incorrect premise. A lone reviewer with a demonstrated input-to-failure path should outrank several unsupported assurances. A clean review means no validated findings under those reviewers' context, not proof that the artifact works.

The stronger evidence mechanisms are in the verification generator and benchmark checklist: observed action plus resulting state, side effects, exact command/revision, error count, completed-work count, and preserved artifacts. Even these claims are bounded by the tested scenario and environment. One screenshot cannot prove persistence. One recipe does not prove all entry points. A transcript that shows a skill file was opened establishes access, not comprehension. A pixel diff establishes only the compared pixels and states. Preserve the boundary between observed, inferred, and untested.

## Plan schema validation is narrower than verification

`check-plan.mjs` is a real structural checker. It validates H1/H2 sections, prescribed blocks and ordering, repeated rule text, lane numbers 1-10, screenshot-shaped strings, `Pass when` wording, four perf labels, review-gate words, and selected style punctuation. It outputs counts and errors. Source: `skills/poteto-mode/scripts/check-plan.mjs:5-29,74-106,117-167,182-185`.

It does not start an app, run a unit test, sample performance, check the current SHA, inspect a screenshot, establish that an artifact exists, validate the predicate's truth, or authorize a merge. It cannot tell whether ten lanes cover distinct risks. Those would require execution receipts and artifacts. Passing this checker means the plan has the prescribed shape; it is not a runtime safety guarantee. A future implementation can keep structural validation while making lane count variable and checking applicable evidence contracts explicitly.

The coordinating audit also ran a concrete format probe, retained in `audit/probe_pstack_plan.py` and `audit/plan-probe/`. It extracted the source template and filled only the model. The ten-lane template exited 0 despite unexecuted boxes, remaining placeholders, and no screenshots. Removing lane 10 exited 1 because the checker expected 1 through 10. This confirms the distinction between required text and verified execution. The probe does not test any application or PR merge behavior.

## Dependencies that are outside the package

The plugin manifest points at `skills/` and `agents/`; these workflow files are packaged instructions rather than a bundled multi-model scheduler. `README.md:231-239` explicitly excludes `deslop`, `control-cli`, and `control-ui`, which belong to `cursor-team-kit`, and `create-skill`, which is a Cursor built-in. `poteto-mode/SKILL.md:23-30,93-95` routes to those capabilities and assumes Cursor Task behavior, background agents, cloud/local execution, per-role model settings, and MCP access semantics. Reading or copying a skill does not supply any of those facilities.

Carry over the portable contracts, then bind them to the available runtime: scoped worker prompts; own output locations; exact revisions; controlled app startup; stable browser/CLI/API drivers; real observation; evidence retention; and honest gaps. On Windows, replace `/tmp`, PTY/tmux assumptions, `uptime`, `nproc`, and Unix process recipes with equivalent supported tools. Keep model roles configurable rather than copying source slugs. Count a substituted reviewer as its actual model and report capability gaps.

The guide calls Comment Sicko a read-only reviewer (`docs/guide/05-build-and-clean.md:69`), while the actual agent says it touches comments and reports deletion counts (`agents/comment-sicko.md:28-32`), and `no-comments` tells the parent to inspect its diff (`skills/no-comments/SKILL.md:20`). This is an instruction-level inconsistency; no runtime read-only enforcement is demonstrated here. The safer carry-over is an explicitly read-only report, followed by reviewed parent edits and behavior checks where comments or suppressions protect a contract.

The useful common thread is concrete obligations that a coordinator can verify. The worker count, persona, prose schema, and particular model are optional machinery. Evidence of the actual artifact and behavior remains the adoption criterion.
