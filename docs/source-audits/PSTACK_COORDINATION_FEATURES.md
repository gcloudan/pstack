# pstack coordination, autonomy, installation, and adoption audit

Source snapshot: `cursor-plugins` commit `23e4138daa01c42d4969f7a5465f82704e64f798`. The pstack manifest reports version `0.15.6`. This is a source audit of the named coordination slice, including its helper scripts and Benny automation pack. No private transcripts were read. No upstream sources or installed kit files were changed. No Cursor cloud run, Slack integration, live automation, or deletion was executed. Ratings assess adoption value from the code and instructions, not observed completion rates.

For a user who wants adaptable workers and little micromanagement across Cursor projects, pstack's best contribution is its contracts: isolate writers, make acceptance observable, preserve standing orders, prove the current patch, and report exceptions. Its complete overnight and project-program workflows also depend on host capabilities and substantial verification infrastructure. Installing the plugin gives the agent instructions and helper files. It does not create cloud agents, a scheduler, Slack permissions, an app driver, or enforceable merge gates.

## Rating scale

5 means adopt broadly with little adaptation. 4 means strong value after small local changes. 3 means useful selectively, with meaningful dependencies or policy adaptation. 2 means an optional specialist workflow requiring substantial adaptation. 1 means unsuitable as a general work default. A low rating can coexist with strong individual ideas.

## Adaptive coordination versus fixed ceremony

The source contains real adaptation, not just a fixed worker list. Code delegates tier by difficulty. Fresh workers receive consolidated scope; a running server, watcher, checkout, or uncommitted state justifies reuse. Orchestrate collapses a small program into direct execution, uses fewer broad workers, adds sub-coordinators only beyond one drain's capacity, fills a rolling window, and uses a dedicated verifier only when a cheap single command is insufficient. Failure modes change the next attempt: smaller scope for cap/OOM, same task for a network failure, a different model for tool errors, one retry for unknown failure, then abandonment/replanning. These are concrete ways the agent can manage itself. [Mode delegation], [Orchestrate]

There are also rigid policies. One cloud owner per PR, all shipping verifiers in cloud, every-hour audit ticks, default named model families, mandatory ten live lanes in plans, ready-never-draft PRs, comment/prose bans, and a coordinator prohibited from writing code are not prerequisites for correctness in every project. Orchestrate's risk-scaled verification contrasts with Multi-phase plan's uniform ten-lane/perf requirement. A general work setup should preserve the acceptance and independence requirements while making counts, placement, cadence, model selection, and PR form depend on task risk, host capacity, and repo conventions. [Shipping], [Plan], [Autopilot full], [Orchestrate]

No human micromanagement does not mean zero human decisions. The useful goal is one initial contract: scope, done predicate, spend/time budget, external-write permission, landing authority, and irreversible boundaries. The agent then owns task decomposition, worker replacement, bounded retries, evidence collection, review-noise triage, and checkpoints. Only product choices, permission limits, and actual dead ends return to the user. The guide supports this framing; base mode's blanket permission for external writes needs to be replaced with the work environment's authorization. [Mode autonomy], [Guide overnight]

## Runtime and dependency reality

The helper tools are narrower than the coordination rhetoric. `orch` is a plain-file bookkeeping CLI. Its command surface covers units, inbox, ledger, gates, standing orders, frontier, and derived status. The playbook explicitly says it never spawns, waits, or wakes an agent. `store.ts` has atomic writes and a PID lock with stale-holder handling, useful structural protection against concurrent file corruption. Its ledger records/checks `(PR, SHA)` rows supplied by the caller; it does not run the verifier, validate that evidence exists, or enforce a merge approval. `frontier set` shells out to Graphite's `gt log short --stack --reverse` and `gt info`, then resolves branch SHAs. Passing `--prs` validates against Graphite's result; it is not a Graphite-free alternate data source. [Orch CLI], [Orch store]

`watch-pr` is a real GitHub-specific read/poll CLI using `gh`, with single, stack, frozen queued-stack, and status-only modes. Its defaults are 60-second polls, five query errors, and no deadline. It emits machine-readable verdicts; the agent must act on them and stop/rearm correctly. It does not merge, create cloud agents, or cover Origin. The entrypoint and `orch` bootstrap use Bun and can automatically install dependencies with `bun install --frozen-lockfile`. A writable installation area, network or cached packages, and Bun are therefore part of the execution environment. [Watcher], [Bootstrap], [Tools package]

`check-plan.mjs` is real structural validation. It checks exact headings, prose punctuation, verification phrases, ten numbered lanes, screenshot names, pass predicates, review/media sections, and perf item labels. It does not validate that a scenario proves the goal, a metric is useful, a screenshot exists, or a checked box reflects a real run. A syntactically valid plan can still be poor. [Plan checker]

The plugin's full mode references `/deslop`, `control-cli`, and `control-ui` from `cursor-team-kit`, plus Cursor's built-in `create-skill`. Autonomous behavior uses Cursor's built-in `/loop`; cloud placement, agent state, stores, and background execution need host support. Ordinary PR operations use `gh` by default or Origin when usable. Orchestrate additionally requires Graphite. Integration-enabled history/issue workflows need credentials and adapters, not merely skill discovery. [README dependencies], [Autonomous run], [Orchestrate]

Make Bot UI has an even narrower host assumption. Its `update_state` routine creation, secret-request card, connector credential file, routine panel, and `<webhook_event>` wake format are operational host interfaces described in a Markdown skill. The manifest does not implement them. Do not interpret installation as availability of a Grok Bot API. The skill also prescribes a Linux Tailscale install shell command and HTTP access to a server bound to all interfaces. The harmless wake probe and server-side key are good checks; access to the UI itself, path translation, process lifetime, secret-file permissions, and tailnet policy still need local decisions. [Bot UI], [Manifest]

Benny is deliberately different from an ordinary slash skill. Its setup and operational files live under `automations/benny/`, outside the manifest's `./skills/` root. Installing pstack leaves it dormant. Setup copies the pack into the target repo, enables shared pstack skills in project settings, keeps user-owned config outside the pack, and verifies dependencies from a fresh project agent. Then two actual automations must be created through built-in `/automate` and its reviewed editor flow. Updates to existing automations are an editor checklist for the user. No automation backend, Slack client, issue tracker, or UI adapter is shipped here. [Benny entry], [Benny setup]

For Benny, preserve fail-closed behavior rather than loosening missing-tool checks to make setup feel easy. Triage needs thread reads/replies, attachments, tracker search/read/create/update and compensation. Repro needs trusted triage identity, repo/PR access, exact mapped UI behavior, read-only inspection, screenshot/recording, baseline/patched builds, and cleanup. Worker tool isolation must exclude Slack writes and credentials; a prompt prohibition is not access control. Configuration is a template, not an automatically validated schema or running service. [Benny setup], [Benny triage], [Benny repro], [Benny control], [Benny configuration]

## Concrete portability and coherence gaps

1. **Graphite is still required in the program path.** Babysit, Shipping, Opening PR, and both autopilots say not to require `gt`. Orchestrate's stack safety explicitly makes Graphite authoritative, and its supplied frontier code calls `gt` directly. This can be read as a workflow-specific dependency, but users need to know the mode switch changes prerequisites. [Orchestrate], [Orch store], [Opening PR]
2. **Installed-plugin paths are assumed to exist in project trunk.** Autopilot audit ticks and the plan skeleton read `origin/main:pstack/skills/...` every tick. A marketplace install can live in a plugin cache, outside the target repo, so those literal paths need a stable accessible source or a resolved installation pointer. Likewise helper command paths and hard-coded `origin/main` need the project's default-branch and install location. [Autopilot full], [Autopilot stack], [Plan]
3. **Cleanup path enumeration loses spaces.** `worktree-audit.sh` uses `awk '/^worktree /{print $2}'` for worktree paths. A path such as this workspace's `.../investigate pstack` truncates at the space. The script also uses BSD `stat -f '%m %N'`, `date -r`, macOS simulator tools in the playbook, and a derived Cursor transcript slug. These are source-observed portability problems, not a tested safe cross-platform implementation. [Worktree audit], [Cleanup]
4. **Untracked work and closed PRs can be misclassified.** The script labels all `??` entries as `scratch`, while the playbook says scratch is safe to drop after naming files. Untracked files can contain real work. The script's `safe` bucket also accepts any non-OPEN PR reference, including CLOSED without merge. The playbook's candidate/in-use review is essential; the bucket cannot authorize deletion. [Worktree audit], [Cleanup]
5. **Cleanup audit is not strictly side-effect-free.** The script describes itself as read-only but fetches `origin main`, which updates local refs, and reads scoped transcripts. It does not delete worktrees. No transcript scan was run during this audit. [Worktree audit]
6. **Pause triggers and inherited claims need clear semantics.** The main index mentions restart/compaction while the pause leaf says explicit only. Pickup prohibits redoing earlier proof yet requires checking inherited claims. Preserve work and intent, but use current artifact state for safety decisions. [Mode], [Pause], [Pickup]
7. **Global style and model config do not inherit automatically.** The personal-mode generator does not guarantee router composition; the global role rule relies on skills following textual role names. Make the relationship explicit and verify it in a fresh session. [Automate me], [Setup]
8. **Verdict styles differ by workflow.** Shipping accepts `PASS+NOTES`; full autopilot's clean verdict sends proven defects filed as notes back to the owner. Different strictness is reasonable, but a status label from one workflow is not automatically a valid gate in another. [Shipping], [Autopilot full]

## Entire upstream versus cherry-picking

Installing the complete upstream plugin is the lowest-maintenance route to its internal skill links, agent names, reference files, and scripts. It preserves update provenance and gives a personal mode access to the available base machinery. Install `cursor-team-kit` as well when its control/deslop paths are needed, configure models once, and demonstrate one small real project task before relying on long runs. This is an adoption recommendation based on the dependency graph, not a claim that marketplace installation was tested in this audit. [Manifest], [Guide setup], [README dependencies]

Complete installation does not require invoking every skill or adopting every author policy. Keep it available as a library. A user-level personal mode can state desired writing, delegation, budget, and external-write boundaries, then explicitly route to applicable pstack workflows. Project-local rules should supply verifier commands, supported branch/PR policy, and tool permissions. Avoid replacing upstream files simply to change tone or model slugs.

Cherry-picking is viable when the subset is intentional and versioned. Copying `poteto-mode` alone leaves dangling playbook/leaf/tool references. Copying a playbook can still omit `show-me-your-work`, principle leaves, Bugbot triage, helper scripts, Bun files, or external control/deslop dependencies. Renaming agent/skill identifiers can change routing. Keeping old role rules can pin retired defaults. Keep a dependency inventory, preserve relative directories, record the source snapshot, and test discovery plus one representative run in a fresh project session.

The work-specific policies should be reviewed before broad application: model defaults; permission to send team chat/tickets; ready-versus-draft PRs; squash merges; Conventional Commits; worktree recovery via resets; automatic cleanup; cloud-only workers; loop spend; fixed ten-lane plans; and automatic edits to a broken skill in a separate PR. The checks worth retaining are writer ownership, known acceptance, independent evidence where risk justifies it, current-patch receipts, bounded recovery, durable trail, and explicit landing authority.

For adaptable low-micromanagement use, first adopt the router, isolation, acceptance predicate, decision log, fresh consolidated briefs, and risk-scaled verification. Then add Babysit and the Shipping boundary. Try Autopilot-stack after the real project driver and durable receipts work. Add merge-capable Autopilot-full or Graphite-backed Orchestrate only when those environments and permissions are established. Benny and Make Bot UI are separate integration projects, not features unlocked just by adding the plugin.
