# Integrating pstack into your existing harness

You are adopting useful working methods from the entire pstack, one feature at
a time. You are not adopting every original default merely by cloning it.

The repository has two layers. `upstream/pstack` preserves all 160 tracked files
from the pinned upstream commit. `skills`, `agents`, `rules` and `profiles`
contain the selected working adaptations. `adoption.json` records each original
skill, principle, playbook and worker separately. The full feature review ranks
what is useful and which assumptions need changing.

## What the first batch changes

The first batch handles understanding an existing subsystem and coordinating
independent investigations. It starts with a compatible recipe already in the
project. If none fits, the adapted router selects the implementation walkthrough
or current-state onboarding workflow. A small question stays with one worker.
A broader question can use separate responsibilities, with counts chosen from
the actual work and available capacity.

Each worker gets the question, its responsibility, permitted actions, starting
pointers and the evidence expected back. It chooses its own searches. The
parent checks material findings and reports missing coverage. Finding one answer
does not finish a task that requires several independent slices.

Compared with the original `how`, this drops its fixed 2–4 exploration angles
and mandatory separate synthesis structure. Compared with the broader original
router and swarm, it defers to your existing workflows and actual runtime.
It does not import author-specific model panels, cloud fleets or delivery rules.
The personal builder remains available for later selected-history adaptation.

## What has actually been exercised

- A source walkthrough found the active entry point, identified unreachable
  legacy behavior and exposed disagreement between the README and running code.
  Existing Node checks passed. This was a bounded fixture, not a productivity benchmark.
- A second fixture already had a project walkthrough recipe. The router followed
  that recipe instead of imposing a duplicate process; its checks passed.
- Both installers copied supporting resources and preserved customized packages
  by default. Explicit replacement made an exact backup. Unrelated skills,
  rules, agents and extra resources survived.
- An independent source/dependency review caught line-ending conversion and an
  unsafe custom-root arrangement. Source bytes were restored from pinned Git
  blobs; installers now reject layouts that would break the worker contract.

These checks establish the prepared integration. They do not establish that
your work Cursor has loaded it. The work harness location has not been supplied,
so its specific rules and existing workflows have not been merged or audited.

## Integrating with the work harness

Clone this repository on work. Supply the target project's directory or harness
repository to the agent. Have it compare the existing rules, skills and agents
with the selected profile before running the installer. A project install adds
a namespaced rule and preserves differing files; a user install shares the core
across projects and needs the documented User Rule activation.

Keep your current project instructions. The added router is meant to fill gaps
and use compatible existing recipes. Do not replace your personalized mode with
a repository seed without reviewing the difference. Check discovery in a fresh
Cursor chat, then exercise one real task before applying it across projects.

## The next feature, every time

1. Pick a concrete need and its upstream feature in the adoption review.
2. Compare it with the target harness: keep existing equivalent behavior.
3. Port only useful missing behavior, together with necessary dependencies.
4. Exercise a permitted task that could reveal failure, then record evidence
   and remaining gaps in the adoption ledger.
5. Add the adapted component to the installation profile and verify discovery
   and real task use in Cursor.

`/pstack-adopt` provides this workflow. Source preserved, instructions adapted,
behavior tested, files installed and live behavior observed are separate states.
The current next candidates are `blast-radius`, reusable verification skills,
then `tdd` and `architect` if your harness lacks those methods. They are queued,
not enabled by this first batch.
