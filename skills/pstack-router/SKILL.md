# Add pstack to the existing harness

Read the current request and applicable project rules first. Find the existing
workflow for the task from the skills and instructions actually available.
Prefer a compatible project-specific recipe over a duplicate generic process.
Use this layer to supply a missing investigation or coordination contract.

Load only the relevant route:

| Request | Route |
|---|---|
| How implementation works, active callers or ownership | [pstack-how](../pstack-how/SKILL.md) |
| Repository current state or onboarding | [repo-onboarding](../repo-onboarding/SKILL.md) |
| Independent coverage or explicitly requested parallel work | [pstack-swarm](../pstack-swarm/SKILL.md) |
| Capture or update personal preferences | [automate-me](../automate-me/SKILL.md), only when requested |
| Adopt another pstack feature into the harness | [pstack-adopt](../pstack-adopt/SKILL.md) |

For bug fixes, features, refactors, performance, reviews and shipping, use the
existing project workflow and tools. Those upstream playbooks are preserved
in the fork but have not been integrated in this first batch. If no suitable
recipe exists, carry out the authorized task directly with proportionate
checks; do not claim to have invoked an uninstalled workflow. Propose an
adoption only if its missing mechanism would help this work.

An investigation explains current behavior. It does not authorize repairs.
Delegation depends on useful independent responsibilities, available tools and
the task's permissions, not a fixed worker count or a forced model panel.
The parent owns the final answer and checks consequential source/evidence.

Keep project constraints, credentials, app commands and delivery policy local.
This router does not grant external messaging, merging, deployment or runtime
capabilities. Apply the user's existing preferences and opt-outs.
